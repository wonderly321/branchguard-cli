# BranchGuard 迭代计划

## 开发原则

- 先验证真实需求，再扩展功能。
- 先 CLI，后插件。
- 先 read-only 检测，后报告和团队协作。
- 每一版都能在真实 Git 仓库中运行。

## 阶段 0：准备和验证

目标：确认需求、技术路线和最小演示场景。

任务：

- 确认产品名。
- 确认开发语言。
- 创建 GitHub 仓库。
- 写 README 草稿。
- 准备 3 个测试仓库场景：
  - 无冲突。
  - 普通文本冲突。
  - lock file 高风险冲突。

完成标准：

- README 能让陌生开发者理解工具用途。
- 手动命令能证明 Git 底层检测可行。

建议时间：1-2 晚。

## 阶段 1：MVP CLI

目标：完成可用的 `check` 命令。

任务：

- 搭建 CLI 项目结构。
- 实现 `branchguard --version`。
- 实现 `branchguard doctor`。
- 实现 `branchguard init`。
- 实现 `branchguard check <base> <head>`。
- 调用 `git merge-tree`。
- 解析冲突文件。
- 实现风险等级。
- 实现配置文件高风险和忽略规则。
- 实现 exit code。
- 实现 `--json`。

完成标准：

- 在真实仓库中能检测两个分支冲突。
- 有冲突时返回 `2`。
- 无冲突时返回 `0`。
- 错误时返回 `1`。
- JSON 输出可被脚本读取。

建议时间：1-2 周。

## 阶段 2：冲突矩阵

目标：技术负责人可以查看 base 与多个分支的冲突情况。

任务：

- 实现本地分支枚举。
- 实现 `branchguard matrix --base main`。
- 输出表格。
- 支持 `--json`。
- 增加 `--limit`，避免分支过多时运行太久。

完成标准：

- 能显示每个分支相对 base 的冲突文件数量和风险等级。
- 10 个分支以内运行体验可接受。

建议时间：3-5 晚。

## 阶段 3：真实用户试用

目标：验证是否有人真的需要。

任务：

- 打包 Windows/macOS/Linux 二进制。
- 写安装说明。
- 写 30 秒演示 GIF 或录屏脚本。
- 找 20 个开发者试用。
- 在 V2EX、掘金、微信群或朋友圈收集反馈。

要问的问题：

- 你最近一次 Git 冲突是什么时候？
- 你会在合并前运行这个命令吗？
- 输出哪些信息最有用？
- 你愿意为团队版付费吗？
- 你更想要 CLI、VS Code 插件，还是 CI 检查？

完成标准：

- 至少 20 个真实试用。
- 至少 5 条有效反馈。
- 至少 1 个明确付费意向。

建议时间：1-2 周。

## 阶段 4：v0.2 产品化

目标：从“能用”变成“愿意推荐”。

任务：

- 优化输出文案。
- 支持 `.branchguard.json`。
- 支持 ignore patterns。
- 支持 high risk patterns。
- 增加 HTML 报告。
- 增加 GitHub Action 示例。
- 增加更多测试 fixture。

完成标准：

- 一个小团队可以把它加入合并前检查流程。
- README 里有完整 CI 示例。
- GitHub Release 可稳定安装。

建议时间：2-3 周。

## 阶段 5：商业验证

目标：验证 Pro / 团队版付费。

可能的付费功能：

- 团队冲突报告。
- 飞书/钉钉通知。
- GitHub Action 注释 PR。
- 冲突责任人识别。
- 团队规则配置。
- 私有仓库批量检查。

最小付费实验：

- 手动 license key。
- 买断价人民币 99-299。
- 给前 20 个用户终身授权。

完成标准：

- 有第一笔收入。
- 至少 3 个用户愿意为某个团队功能明确付费。

## 每周工作节奏

适合有主业的节奏：

- 工作日晚上：每晚 1-1.5 小时，做一个小任务。
- 周末：半天开发，半天打包/写文档/找用户。

建议节奏：

- 周一：确定本周一个目标。
- 周二到周四：实现功能。
- 周五：补测试和 README。
- 周末：试用、修 bug、收反馈。
